# 把任务描述清楚

上一课你看到，Codex 能听懂一句简单的话并完成任务。但任务越复杂、项目越大，描述的
质量就越影响结果。这一步你练习怎么把任务说清楚，让 Codex 准确做出你要的效果。

## 先看一条简单的描述

回忆一下上一课，你给 Codex 的任务其实很朴素："创建一个脚本，打印一行问候语。"
Codex 也能做对。但当你想改的不只是一个小脚本时，这种简单描述就可能出问题：它不知道
你要改哪个文件、按什么标准算做完、有哪些不能动的地方。

现在做一次对比练习。在同一个 `codex-practice` 目录里，让 Codex 给已有的
`greet.sh` 加一个功能：每次运行时，除了打印问候语，还要打印一行当前时间。

先让学生（也就是你自己）写一条描述，发给 Codex，看它做出来什么样。

## 用四个要素把任务说完整

一份清楚的任务描述，通常包含四样东西：

- **目标**：你要把什么做完、做成什么样。
- **上下文**：涉及哪些文件、目录、文档或已有的代码。
- **约束**：要遵守的标准、约定，以及不能改动的东西。
- **完成标准**：什么情况算做完，比如某个测试通过、某个输出符合要求。

把这四样都写上，Codex 就不容易跑偏，也不会凭假设去猜你没说出口的要求。下面是一个
结构完整的描述，同样实现"打印时间"这个功能：

```text
目标：让 greet.sh 每次运行时都打印当前时间，格式为 YYYY-MM-DD HH:MM。
上下文：只改 codex-practice 目录里的 greet.sh，不要新建其他文件。
约束：保留原有的问候语输出，不要改动脚本已有的其他内容。
完成标准：运行 ./greet.sh，能同时打印问候语和格式正确的当前时间。
```

对比一下你之前写的那条描述和这条。看看四要素里，你之前少了哪些，少了这些可能让
Codex 在哪些地方猜错。

## 具体改一改

把上面这条描述发给 Codex，让它修改 `greet.sh`。观察它怎么做：它是不是先读了
`greet.sh` 的现有内容，然后只改动需要改的地方。

如果你让它"同时打印问候语和时间"，但它把原来的问候语删掉了、或改了格式，那就是
描述里少了约束，或者约束不够明确。这时不要直接接受结果，指出问题让它重做，比如
回复："约束没满足：问候语还在吗？格式要保持原来的。"

## 让 Codex 先给方案

对于比较复杂的任务，你还可以让 Codex 先出方案、不要直接动手。这样你可以先确认
它理解对了，再让它执行。在 CLI 里，`/plan` 可以进入计划模式，Codex 会先收集上下文、
问清疑问、给出计划，再开始实现；你也可以直接在任务里要求"先给出方案，等我确认
再动手"。

这正对应访谈里你选的练习方式：如果你希望"先给方案、确认后再改"，就用这种方式。

## 检查你的结果

任务做完后，自己验证，不要只信 Codex 说它完成了：

```bash
./greet.sh
```

检查两点：问候语还在，并且多出了一行格式正确（`YYYY-MM-DD HH:MM`）的当前时间。
两者都满足，才算这个任务真正完成。如果时间格式不对、或问候语没了，说明还没完成，
继续让 Codex 修正。

## 试试更复杂的任务

趁热打铁，用四要素写一条更完整的任务，看效果有没有不同。比如：让脚本在打印时间和
问候语之外，再统计并打印这是第几次运行。

写这条描述时，把四个要素都明确写出来，尤其是"完成标准"。运行脚本，确认输出符合
你的完成标准。

## 记住这个方法

把任务拆成目标、上下文、约束、完成标准这四样，写清楚，是让 Codex 稳定做出你要的
效果的关键。任务越大，这个方法越重要。后面的练习都会用到它。
