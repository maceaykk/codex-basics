# 在真实项目里协作改代码

前两课都是在练习目录里跑小脚本。这一步你让 Codex 进入一个用 Git 管理的真实项目，
改代码、跑测试。这一步会用到 Git：有了版本管理，你可以放心让 Codex 改，不合适就
回退重来。

## 先建一个带测试的项目

在练习目录里，建一个带测试的 Node.js 小项目。先新建项目目录并进入：

```bash
mkdir string-tools
cd string-tools
git init
```

创建 `string-tools.js`，放一个简单的字符串工具函数：

```js
// string-tools.js
function uppercase(input) {
  return String(input).toUpperCase();
}

module.exports = { uppercase };
```

再创建测试文件 `string-tools.test.js`，用 Node 内置的测试模块，不需要安装任何依赖：

```js
// string-tools.test.js
const test = require("node:test");
const assert = require("node:assert");
const { uppercase } = require("./string-tools.js");

test("uppercase 转成大写", () => {
  assert.strictEqual(uppercase("hello"), "HELLO");
});
```

运行测试，确认当前项目是好的：

```bash
node --test
```

看到测试通过（`# pass` 为 1），说明项目和测试都没问题，可以作为起点。

## 用 Git 建立基线

在让 Codex 改动之前，先把当前状态提交为一个基线。这样之后的所有改动都能被清晰
对比和回退。

```bash
git add .
git commit -m "初始版本：含 uppercase 函数及其测试"
```

提交信息由你来写，写清楚这次提交是什么。提交完成，你就有一个干净的起点。

## 让 Codex 加一个功能

现在给 Codex 一个真实的功能需求，让它在这个项目里实现。先自己用四要素把任务描述
写清楚，再发给它。默认建议是加一个反转字符串的函数 `reverse`，并配测试。

```text
目标：在 string-tools.js 中新增一个 reverse 函数，把输入字符串反转后返回。
上下文：只改 string-tools.js 和 string-tools.test.js，不要改动已有的 uppercase 函数。
约束：保持现有代码风格，不要引入新的依赖。
完成标准：运行 node --test，uppercase 和 reverse 两个测试都通过。
```

发送之前先猜一猜：Codex 会改哪些文件？它会保留已有的 uppercase 函数，还是可能重写
整个文件？测试在哪个环节会起作用？记下你的猜测，等它做完对照。

观察 Codex 的做法：它是否先读了现有文件、理解了风格，再动手；是否只加了需要的内容；
有没有动到不该动的地方。

## 用测试验证

Codex 说做完后，不要直接相信。自己运行测试验证：

```bash
node --test
```

两个测试（`uppercase` 和 `reverse`）都通过，功能才算真的完成。如果有测试没通过，
或 `reverse` 的行为不对，那就是没完成，继续让 Codex 修复，直到全部通过。

测试在这里扮演的角色，是给你一个客观的"完成标准"：不靠主观感觉，靠命令输出判断
Codex 做得对不对。

> 注意计数规则：`node --test` 顶部的数字按测试**文件**计算，不按单个测试计算。一个
> 文件里写了多个测试、全部通过时，顶部仍显示每个文件 1，所以这里两个测试都通过也只
> 显示 `pass 1`。判断是否全部通过，看 `fail 0`（没有失败）和每个测试文件前的对勾
> `✔`，别被 `pass` 的数字误导。

## 用 Git 查看和回退

现在看 Codex 改了哪些内容。运行：

```bash
git diff
```

它会显示自上次提交以来的改动。检查这些改动：是不是只加了 `reverse` 函数和对应测试，
有没有意外改动了其他内容。如果有不该动的改动，说明需要调整。

如果改动不合适，可以干净地回退。确认要放弃这些改动后，运行：

```bash
git restore .
```

这会把工作区恢复到上次提交的状态，改动被丢弃。有了这个兜底，你可以更放心地让
Codex 改，改得不对就回退重来，不必小心翼翼到不敢让它动手。

## 让 Codex 按仓库约定工作

真实项目往往有自己的约定，比如代码风格、测试方式。你可以用 `AGENTS.md` 把这些约定
写下来，Codex 会自动读取并遵循。`AGENTS.md` 相当于给智能体看的说明，放仓库根目录，
可以写构建、测试、命令、约定，以及什么算做完。

让 Codex 帮你生成一份初始的 `AGENTS.md`：

```text
根据当前项目，生成一份简短的 AGENTS.md，说明如何运行测试、代码风格和完成标准。
```

看它写出来的内容符不符合你的实际情况，不合适就让它修改。之后在这个仓库里，Codex
会照着这份说明工作，你的任务描述就可以少重复这些约定。

## 尝试改一改

现在你已经在真实项目里配合 Codex 走完了一轮：定基线、提需求、跑测试、看改动。自己
再加一个小需求，比如让 `reverse` 在输入不是字符串时也能正确处理，看 Codex 能否在
不破坏现有测试的前提下完成。

运行 `node --test`，确认改动生效且所有测试仍通过。
