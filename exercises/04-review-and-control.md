# 审查改动并控制权限

前一课你已经让 Codex 在项目里改代码。但智能体能改东西，就意味着它可能改错、改到不该
改的地方。这一步你学会两件事：看懂 Codex 什么时候需要你批准，以及怎么审查它做出的
改动。这是安全使用 Codex 的关键。

## 两个控制机制

Codex 有两层控制，各管一件事：

- **沙箱模式**：规定 Codex 技术上能做什么，比如能写哪些目录、能不能访问网络。
- **审批策略**：规定什么时候要停下来问你，比如要写到工作区之外、要用网络、要运行
  命令时。

两者配合：沙箱限制住它能触及的范围，审批则在它要越界或做高风险动作时让你把关。

## 认识沙箱模式

常用的沙箱模式有三个取值：

- `read-only`：Codex 只能读取和运行命令，不能改动文件。适合先规划、先讨论，不实际
  动手的场景。
- `workspace-write`：Codex 可以读取、修改工作区里的文件并运行命令。这是默认的自动
  模式，适合在受信任的项目里实际改动。
- `danger-full-access`：不加沙箱，也不问审批，能做几乎一切。风险高，不推荐日常使用。

在命令行里，可以用 `--sandbox` 指定模式：

```bash
codex --sandbox read-only
codex --sandbox workspace-write
```

在交互界面里，也可以用 `/permissions` 命令切换沙箱模式。用 `/status` 可以查看当前
工作区和当前会话的状态，确认现在是什么模式。

## 认识审批策略

审批策略决定什么时候要问你。两个常用取值：

- `on-request`：只有在需要审批的动作（如写工作区之外、用网络）时才停下来问你，这是
  默认的"自动"模式。
- `never`：从不询问，直接执行。适合你完全信任、且不想被打断的场景。

命令行里用 `--ask-for-approval` 指定，它还有短写 `-a`：

```bash
codex --sandbox workspace-write --ask-for-approval on-request
codex --sandbox read-only --ask-for-approval never
```

默认的"自动"组合就是 `workspace-write` 加 `on-request`：Codex 可以读写工作区、运行
命令，但要写到工作区之外、或访问网络时，会先问你。

## 切到只读，先看不动手

回到 `string-tools` 项目，做一次对比。先用只读模式，让 Codex 给你一个改动方案，但不
让它动手：

```bash
codex --sandbox read-only
```

给它一个任务，比如给 `uppercase` 加一个去除首尾空格的 `trim` 功能。在只读模式下，
Codex 只能读文件、给方案，改不了代码。看它给出的方案：它会改哪些文件、加什么代码、
配什么测试。

这时先猜一猜：如果让 Codex 实际动手，它做哪些动作会触发审批？再切到可写模式验证你
的判断。

## 审查一次改动

现在切回可写模式，让 Codex 真正实现这个 `trim` 功能：

```bash
codex --sandbox workspace-write --ask-for-approval on-request
```

Codex 改完后，不要直接接受。审查它的改动，这是你作为人的把关环节。运行：

```bash
git diff
```

逐条看这次改动：是不是只加了 `trim` 和对应测试，有没有顺手改掉无关的代码，风格是否
和仓库一致。审查时重点想：改得对不对、有没有动到不该动的、有没有留下问题。

如果改动合适，运行测试确认功能正常，然后提交：

```bash
node --test
git add -A
git commit -m "新增 trim 函数及其测试"
```

如果改动不合适，就用上一课学的 `git restore .` 回退，让 Codex 重做，或自己调整。

## 理解什么时候会问审批

在可写模式下，Codex 写工作区里的文件、运行命令一般不需要问。但当它要做这些时，会
停下来等你：

- 修改工作区之外的文件。
- 运行需要访问网络的命令。
- 其他被沙箱判定为越界或高风险的动作。

审批请求出现时，先看清它想做什么、有没有风险，再决定同意还是拒绝。不要把审批当作
麻烦、习惯性全点同意——审批的意义就在于，让你在关键动作上做判断。

## 读配置，固定你的偏好

不想每次敲参数，可以把偏好写进配置文件。个人默认配置在 `~/.codex/config.toml`，
某个仓库的特定配置可以放在仓库里的 `.codex/config.toml`。

比如想固定为"可写工作区、按需审批"：

```toml
approval_policy = "on-request"
sandbox_mode    = "workspace-write"
```

想更保守、只读规划：

```toml
approval_policy = "on-request"
sandbox_mode    = "read-only"
```

改完配置，再运行 `codex` 就会按这个配置来。注意：配置文件里的值会长期生效，改之前
想清楚是不是你真要的。

## 记住安全原则

默认保持收紧的权限，先理解工作流，再按需放宽。对于受信任的仓库、明确的任务，再考虑
放宽到更自主的模式。不要为了省事一开始就给 Codex 全部权限，等出了问题再收紧。

如果确实需要不打断地连续执行（比如跑一个自动化任务），可以用非交互的 `codex exec`：

```bash
codex exec --sandbox workspace-write "你的任务描述"
```

它按任务一次性执行，适合脚本化、重复的场景。但同样要从紧的沙箱开始。
