# 应对错误并迭代调整

前几课里，Codex 大多一次就做对了。但真实使用中，它做不对、做错、或结果不符合预期是
常态。这一步你练习当 Codex 失败时怎么应对：看问题、定位原因、纠正、回滚，并复测。
学会这套流程，你才敢放心地把更重要的任务交给它。

## 先看问题，别急着接受

回到 `string-tools` 项目。这次给 Codex 一个带点陷阱的任务，看看出错时怎么处理。
比如让它给 `uppercase` 加一个功能：处理输入为空的情况，空输入返回空字符串。

```text
目标：让 uppercase 在输入为空字符串或 null 时返回空字符串，其余情况保持大写。
上下文：只改 string-tools.js 和 string-tools.test.js。
约束：不要改动已有的 uppercase 默认行为。
完成标准：运行 node --test，包含空输入和 null 输入的测试都通过。
```

故意让这个需求带点模糊，或在 Codex 完成后指出它没满足的地方。当 Codex 交出来的结果
测试没通过、或行为不符合要求时，先别接受，也别直接让它"重做"。先看清楚问题。

## 看报错和改动

先运行测试，把失败信息读出来：

```bash
node --test
```

看失败的测试是哪一条、期望值和实际值是什么，报错指向哪个函数。再运行：

```bash
git diff
```

看 Codex 这次到底改了什么。自己先猜一下：问题出在哪个函数、是逻辑写错了、还是漏了
某种情况。把你的猜测写下来。

## 让 Codex 定位和修复

把你的观察和猜测告诉 Codex，让它一起定位。比如：

```text
测试失败了，报错显示空输入这一情况没被正确处理。先看 git diff 确认改动，
定位问题出在哪，再修复，最后重新运行 node --test 验证。
```

在让它修复之前先猜一猜：它这次的修复会不会引入新问题？你打算怎么验证修复真的生效了？

看 Codex 怎么做：它是只针对失败的那一处做最小修改，还是顺手大改一通。理想情况下，
它定位准确、改动聚焦，并主动重新跑测试确认。

## 复测，确认真的修好

Codex 说修好了，不要相信，自己复测：

```bash
node --test
```

这次所有测试都通过，才是真的修好。如果还有测试没通过、或你怀疑修复引入了新问题，
就继续让 Codex 调整，再复测，直到测试真正通过。

复测是这一课的核心：不靠 Codex 的自述，靠你自己运行命令、看输出，确认问题真的解决。

## 该回滚时回滚

有时候 Codex 的修复越改越乱，或改错了方向。这时与其让它在错误的基础上继续改，不如
回退到上一个干净状态再重来。

如果这次改动不合适，确认要放弃后运行：

```bash
git restore .
```

工作区回到上次提交的状态。然后重新给 Codex 更明确的描述，让它从干净状态重新实现。
回滚不是失败，而是让 Codex 从一个可靠的起点重来，往往比在错误上修补更快。

## 学会描述"错在哪"

让 Codex 有效修复的关键，是把你的观察讲清楚。描述修复任务时，同样用四要素，但要
带上具体的错误信息：

- **目标**：要让什么通过、达到什么结果。
- **上下文**：哪个测试失败、报错信息是什么、改了哪些文件。
- **约束**：要保留什么、不能动什么。
- **完成标准**：复测命令的输出要是什么样子。

错误信息越具体，Codex 定位越准，修复越不容易跑偏。含糊地说"改一下，不对"，往往得
不到好结果。

## 试一次更棘手的错误

现在自己制造一个更真实的局面，走一遍完整流程。比如让 Codex 改一个已有函数的行为，
然后故意指出一个它没考虑到的边界情况，看它怎么定位、修复、复测。

全程自己做三件事：看报错、看改动、复测。确保最终测试通过、结果正确。

## 记住这套流程

出错时的标准流程是：先看报错和改动、定位问题、给 Codex 一个讲清楚错在哪的任务、
修复后自己复测，改不下去就回滚重来。这套流程能帮你在 Codex 出错时保持主动，而不是
被动接受一个有问题的结果。
