# 做一个自己的小工具

这是最后一课。前面你学了安装、描述任务、在项目里协作、审查控制、出错调整。这一课
你把这些都用上，用 Codex 从零做一个带测试的小工具，自己验证、审查，并决定怎么收尾。

## 定下你要做什么

先定下这个小工具要做什么。建议选一个简单、能手动验证的文本小工具，比如一个能统计
一段文本字数和行数的脚本，或一个能对文本做某种转换的工具。

想清楚两件事，并写下来：

- **这个工具做什么**：输入什么、输出什么、边界情况怎么处理。
- **怎么算做完**：用测试和一次手动运行来验证。

这里要把访谈里你选的方向用上：如果你最想做的是改现有项目，就挑一个你已有的小项目，
让 Codex 加一个功能；如果你想练基本功，就选最简单不过的工具，把重点放在描述和验证。

## 建项目并定基线

和第三课一样，先建一个带 Git 的项目。在练习目录里：

```bash
mkdir my-tool
cd my-tool
git init
```

让 Codex 先帮你搭一个最小的可运行骨架：一个主脚本、一个用 `node:test` 写的测试文件、
以及一份 `AGENTS.md`。这一步先给方案、不要直接动手：让 Codex 先给出项目结构、文件
划分和测试计划，等你看一遍、确认后再让它创建。

```text
先给出方案，不要动手：规划这个文本小工具的项目结构、需要哪些文件、每个文件做什么、
用 node:test 写哪些测试。等我确认后再创建。
```

看它给的方案：结构是否清晰、测试是否覆盖了关键行为和边界情况。有要调整的地方就提出来，
确认后再让它创建文件。

把当前骨架提交为基线：

```bash
git add .
git commit -m "骨架：主脚本、测试与 AGENTS.md"
```

## 分步实现功能

现在让 Codex 实现核心功能。用四要素把任务写清楚，一次让它做一个明确的部分，不要一次性
把所有需求堆上去：

```text
目标：实现统计文本字数和行数的核心功能，输入一段文本，输出字数和行数。
上下文：在 my-tool 里实现，主脚本和测试文件已有，先看现有内容。
约束：保持现有结构和代码风格，不要引入新依赖，边界情况（空文本）要处理。
完成标准：运行 node --test，所有测试通过，并手动运行脚本确认输出正确。
```

实现过程中，按你访谈里选的方式控制：要"先方案"的，先审它的实现思路再让它动手；要
"直接改"的，让它直接实现，但每完成一部分就停下来，看它改了什么。

每一步完成后，自己运行测试，确认这部分真的通过，再进行下一步。不要攒到最后一起看。

## 自己验证，自己做判断

功能实现完，Codex 说做完了，不要直接接受。做两层验证：

自动化测试，确认逻辑正确：

```bash
node --test
```

手动运行，确认真实行为符合你的要求。比如给它一段实际文本，看输出是不是你要的，边界
情况是不是处理好了。

两层都通过，才算真的完成。测试通过但手动跑出来不对，或手动对但测试没覆盖到关键情况，
都说明还没到位，继续让 Codex 调整。

## 审查改动，决定是否提交

看 Codex 这次改了什么：

```bash
git diff
```

审查改动是否聚焦、有没有动到无关内容、风格是否和项目一致。如果满意，运行测试后提交：

```bash
node --test
git add -A
git commit -m "实现文本统计功能并附测试"
```

如果有不满意的地方，回退到上一个提交重来，或让 Codex 修正后复测。最终是否接受、是否
提交，由你决定。

## 回顾你做的决策

这一课里，真正的决策都是你做的：定工具做什么、审方案、写任务描述、看 diff、跑测试、
手动验证、决定提交或回退。Codex 做的是读取、思考、修改、运行这些执行层面的事。回顾
一下，哪些决策你做得果断、哪些地方你本可以更早介入，这决定了你以后和 Codex 配合的效率。

## 收尾：清理练习资源

练习结束后，清理一下这次产生的资源，但先想清楚要保留什么。

- **本地源码**：`my-tool` 和之前的 `codex-practice`、`string-tools` 等目录。默认建议
  保留，因为它们是你这门课的成果，之后还能改、还能看。
- **临时文件**：练习中可能产生的临时文件或目录，可以清理。
- **云资源**：如果练习中用到了会部署到云端的服务，注意可能产生按量计费的资源，说明
  清楚持续费用。

清理任何内容之前，先跟你确认，不要自动删除，也不要动不属于这次练习的资源。想保留
什么、清理什么，由你决定。清理是可选的，不做也不影响课程完成。
